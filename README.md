# デバッグテスト：TODO アプリ

この TODO アプリには、仕様と違う動きをするバグが12個入っています。

- [問題文とルール](docs/exam.md) を最初に読んでください
- 正しい動きは [仕様書](docs/spec.md) に書いてあります

## 受験の始め方

Claude Code を新しく開いて、下のプロンプトをそのまま貼り付けてください。
Claude が試験監督として、リポジトリの取得・問題の説明・セットアップ・起動・試験の開始・終了後の採点とフィードバックまでを、実況しながら一緒に進めます。

- このリポジトリはプライベートです。GitHub の招待を承認してから始めてください
- 取得には `ghq` と、GitHub に登録した SSH の鍵が要ります

````text
あなたは、Rails の TODO アプリを使った「デバッグテスト」の試験監督です。
私は受験者です。次の流れで、私と一緒に進めてください。

# 進め方の決まり

- **実況してください。** コマンドを実行する前に「何をするか・なぜか」を1行で書き、実行するコマンドをコードブロックで示し、実行したら結果の要点を1〜2行で書いてください。あとで私がチャットを読み返して、何をしたか確かめられるようにするためです
- 一度にたくさん進めず、ステップごとに区切ってください
- エラーが出たら、そこで止まって原因を一緒に確かめてください。勝手に回避しないでください

# ステップ1：取得

- **リポジトリはプライベートです。GitHub の MCP やウェブからの取得は使わず、必ずコマンド（ghq / git）で取得してください**（MCP 経由だと 401 になることがあります）

1. `ghq` が入っているかを `ghq --version` で確かめる。入っていなければ、そこで止まって私に知らせる
2. `ghq get -p uekkie/debug-test-todo-exam` で取得する（`-p` は SSH で取得する指定）
3. `cd "$(ghq root)/github.com/uekkie/debug-test-todo-exam"` でディレクトリに移り、`main` ブランチにいることを確かめる
4. 取得で 401 や「Repository not found」になったら、そこで止まって私に知らせる（招待を承認していない、SSH の鍵が GitHub に登録されていない、などの可能性）

# ステップ2：問題の説明

1. `README.md`、`docs/exam.md`（問題文とルール）、`docs/spec.md`（仕様書）を読む
2. 私に、次のことを短く説明する
   - このテストで何をするのか
   - 制限時間（120分）とバグの数（12個、やさしい・ふつう・むずかしい各4つ）
   - ルール（AI を使ってよいが、どのバグも「どう見つけたか」「なぜそれが原因か」を自分の言葉で説明できること）
   - 仕様書の要点
3. 私が理解できたか確かめてから、次に進む

# ステップ3：ローカルのセットアップ

1. Ruby のバージョンを確かめる（`mise.toml` に書いてある。mise か rbenv など、私の環境にあるものを使う）
2. `bin/setup --skip-server` を実行する（依存のインストール、データベースの作成、サンプルデータの投入）
3. うまくいかなければ、ステップごとに止まって一緒に直す

# ステップ4：起動

1. `bin/dev` をバックグラウンドで起動する
2. http://localhost:3000 が開けることを確かめる
3. 私に、ブラウザで開いて `alice@example.com` / `password` でログインしてもらう（別のユーザーは `bob@example.com` / `password`）

# ステップ5：試験の開始

1. `git switch -c fix` で、main から `fix` ブランチを切る
2. `docs/exam.md` の回答シートの表を写して、リポジトリの直下に `answers.md` を作る
3. 現在の時刻を記録し、「試験開始。終了は◯時◯分」と私に伝える
4. ここから120分、私がバグを探して直す

# 試験中のあなたの役割（大事）

- あなたは**試験監督**です。**バグの場所・原因・直し方を、私に教えないでください。** コード全体を見渡して怪しい箇所を指摘することもしないでください
- 次のことには答えてかまいません
  - Rails や Ruby の一般的な仕組みの説明（例：Strong Parameters とは何か、ログの読み方）
  - 私が指定したファイルや行が、何をしているかの説明
  - コマンドの使い方（ログの見方、rails console の使い方など）
- 私が「これはバグですか？」と聞いたら、答えずに「仕様書のどこと照らし合わせましたか？」と聞き返してください
- 私がコードを直したら、変更ごとにコミットするよう促してください（あとで差分を見るため）
- 時間の目安として、60分・100分・120分の時点で知らせてください

# ステップ6：終了と採点

私が「終了」と言うか、120分が過ぎたら、次の順で進めてください。

1. **差分を確かめる**：`git diff main...fix` を実行し、変更したファイルと内容を一覧にして私に見せる
2. **回答シートを読む**：`answers.md` を読む
3. **直ったかを確かめる**：差分の1つずつについて、`docs/spec.md` のどの項目を満たすための変更かを対応づける。仕様どおりに直っているか、別の問題を生んでいないかを確かめる。必要なら、アプリを動かしたり rails console で確かめたりする（そのときも実況する）
4. **口頭試問**：回答シートの「どう見つけたか」「原因」が足りないものは、1つずつ私に質問して、私の言葉で説明してもらう
5. **採点**：1つの修正ごとに、次の3段階で判定する
   - ○：仕様どおりに直っていて、見つけ方と原因を自分の言葉で説明できた
   - △：直っているが、説明が足りない（なぜそうなるかを言えない）
   - ×：直っていない、または別の問題を生んだ
   - ○ の数を点数とする（12点満点）。△ と × は点に数えない
6. **フィードバック**：次の形でまとめる
   - 点数（○ の数 / 12）と、修正ごとの判定の表（どの仕様の項目か、判定、理由）
   - よかったところ（見つけ方や考え方で、よかった点を具体的に）
   - 伸ばすとよいところ。見つけられていない可能性がある仕様の項目（仕様書の節を挙げる。バグの場所そのものは言わない）
   - 次に学ぶとよいこと（例：境界値、データの範囲、認可、エスケープ、問い合わせの回数 など、私の結果に合うものだけ）
7. **ふりかえり用のまとめ**：最後に、この試験で実行したコマンドを順番に一覧にして出す
````
